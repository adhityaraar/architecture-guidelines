1. HA & DR Principles

All IBM production workloads must meet minimum resiliency standards. This document provides the framework; product-specific guidelines (Db2, DataStage, etc.) are accessed via the tabs above.

PrincipleDefinition
RedundancyNo single component in the critical path should be a single point of failure (SPoF).
Geographic isolationHA targets within a DC; DR targets require a physically separate site.
AutomationFailover for Tier 1/2 workloads must be fully automated — human detection is too slow.
ObservabilityEvery component must emit health metrics; alerts must fire before users notice.
Regular DR testingUntested DR is not DR. Test failover at minimum once per quarter.
Minimal blast radiusDesign so a failure affects only the smallest possible scope of users/services.

2. RPO / RTO Framework

Recovery Point Objective (RPO) defines the maximum acceptable data loss measured in time. Recovery Time Objective (RTO) defines the maximum acceptable downtime after a failure event.

MetricQuestion it AnswersDrives
RPO"How much data can we afford to lose?"Replication mode, backup frequency
RTO"How long can the service be down?"Automation level, standby warm/cold, runbook speed

These security requirements apply to all IBM HA/DR deployments regardless of product.

6. IBM Licensing: Cold, Warm & Hot Standby

Standby Definitions

TypePrimary CopyBackup Copy"Doing Work"?Access to Live Data?Licence Required?
Cold Running Not running (switched off) No Primary: Yes  |  Backup: No No
Warm (not doing work) Running Running / idling No Primary: Yes  |  Backup: No No
Warm (doing work) Running Running Yes — e.g. continuous data replication Primary: Yes  |  Backup: Yes Yes
Hot Running Running Yes — actively shadowing primary Primary: Yes  |  Backup: Yes Yes

Scenario Diagrams

Diagrams reproduced from: IBM Backup and Disaster Recovery Licensing Guide, February 2026. View source PDF

Cold Standby — No Licence Required

Only the primary program is running. The backup program is switched off and must be switched on before it can take over. Data is periodically transferred via backup & restore software.

Warm Standby — Two Variants

The backup program is running ("idling") on the backup server. Whether a licence is required depends on whether the backup copy is doing work.

Variant A — Backup running but NOT doing work  →  No licence required

Variant B — Backup running WITH continuous data replication  →  Licence required

Hot Standby — Licence Always Required

Both the primary and the additional server are actively running the IBM program and doing work. Continuous data replication keeps both in sync. The standby is ready to take over immediately.

What Counts as "Doing Work"?

A backup installation is considered to be doing work when it is accessed by a user or processes data in any of the following ways:

  • Production, development, program maintenance, or testing workloads.
  • Mirroring transactions, updating files, or synchronising programs, data, or other resources.
  • Maintaining an active link, heartbeat, or duplexed/mirrored connection with the primary.
  • Any activity that enables an active hot-switch or synchronised switchover to occur.
Key Rule: Continuous Data Replication = "Doing Work" If the backup copy receives real-time/continuous data replication (e.g. Db2 HADR SYNC or NEARSYNC), the installation is considered to be doing work — even if it is not actively serving user requests. A licence is required for that backup copy. This is the most common cause of unintended licensing gaps in HA environments.

Backup Testing & DR Testing Allowances

Test TypeDescriptionAllowance (no extra licence)
Backup Testing Verify backup facilities work; primary continues running. No production workload on backup during test. 1–3 tests per year, each 2–3 days. More frequent tests permitted if shorter (total hours within guideline).
Disaster Recovery Testing Simulate a real disaster — primary goes offline, backup takes the primary role including production workloads. 1–3 tests per year, each approximately 2–3 days.
DR Running > 3 Weeks If the DR machine takes on the primary role for more than three weeks and requires more licences than the primary machine (e.g. higher PVU count), discuss with IBM to determine if additional licences are required.

Licence Order of Precedence

When determining the exact licensing requirement for any product, apply the following order (highest precedence first):

  1. Specific contractual terms signed with IBM (ELA, ESSO, SSSO).
  2. Offering-specific terms — License Information documents, Licensed Program Specifications, Transaction Documents.
  3. IBM software policies (including the IPLA Backup use policy).
  4. Base IBM licence agreements — IPLA v14/v15, IPAA, IPAEA.

Licensing Tool Guidance

ToolAction Required for Backup Servers
IBM License Metric Tool (ILMT)Exclude (not suppress) unlicensed backup installations in the Software Classification screen. Annotate each exclusion with the standby type and justification (e.g. "Server A is warm backup (not doing work) to Server B").
IBM License Service (containers)Use Kubernetes Annotations to identify and correctly classify backup/DR pods. IBM License Service must be installed on all clusters — including DR clusters — to qualify for Container Licensing. Missing License Service forces Full-Capacity licensing.

7. Universal Pre-Production Checklist

These items apply to every IBM HA deployment, in addition to the product-specific checklists in each tab.

  • Application tier classification documented and approved
  • RPO and RTO targets agreed with application owner and signed off
  • HA topology diagram produced and reviewed by architecture board
  • No single points of failure identified in the critical path
  • All replication links on untrusted networks encrypted (TLS 1.2+)

  • Runbook written, reviewed, and stored in accessible location
  • Failover drill completed and RTO/RPO measured against targets
  • DR test schedule agreed (minimum quarterly for Tier 1/2)

Db2 HADR — Overview

IBM Db2 High Availability Disaster Recovery (HADR)

IBM Db2 HADR replicates log records from a primary to one or more standby databases over TCP. The standby continuously replays logs; on primary failure it is promoted (takeover) to become the new primary.

Goals & Targets

GoalTarget
RPO (SYNC mode)Zero
RPO (NEARSYNC mode)< 2 seconds
RTO (automatic takeover)< 30 seconds
Availability99.99%
Maximum standbys3 (Db2 11.1+)

Core Concepts

TermDefinition
Primary DatabaseActive instance accepting read/write workloads; ships logs to standby(s).
Standby DatabaseContinuously updated replica; can take over the primary role.
Log ShippingRedo log records transmitted from primary to standby over TCP.
TakeoverPromotion of standby to primary — manual, by force, or automatic.
Log GapDifference between primary and standby log sequence number (LSN).
ACRAutomatic Client Reroute — redirects clients after takeover.
Reads on StandbyRead-only SQL directed to standby to offload primary.

Synchronisation Modes

Choose the right sync mode based on RPO requirements and network latency.

ModeCommit AcknowledgementRPOPerf ImpactUse When
SYNCLog flushed to standby diskZeroHigh (RTT)Tier 1 — zero data loss mandatory
NEARSYNCLog received by standby~1 pageMediumLow-latency LAN, sub-second RPO acceptable
ASYNCLog on primary disk onlySeconds–minMinimalWAN DR replication
SUPERASYNCImmediate (no standby ack)UnboundedNoneMonitoring replicas only — NOT for production HA
SYNC over WAN SYNC adds one round trip per commit. For sites > 5 ms RTT apart, use NEARSYNC or ASYNC. Reserve SYNC for same-DC, dedicated low-latency links.

Changing Sync Mode (no restart required)

UPDATE DB CFG FOR <DBNAME> USING HADR_SYNCMODE NEARSYNC
-- Change takes effect immediately; verify with MON_GET_HADR

Peer Window

The HADR_PEER_WINDOW parameter defines how long the primary waits for the standby to acknowledge logs before downgrading to ASYNC mode.

UPDATE DB CFG FOR <DBNAME> USING HADR_PEER_WINDOW 120  -- seconds
-- A value of 0 disables the peer window (not recommended for Tier 1)

Configuration Reference

Complete parameter reference for setting up Db2 HADR from scratch.

Step 1 — Prepare Both Nodes

-- Take a full offline or online backup of the primary
db2 BACKUP DATABASE <DBNAME> ONLINE TO /backup/ INCLUDE LOGS

-- Restore onto standby (different hostname)
db2 RESTORE DATABASE <DBNAME> FROM /backup/ LOGTARGET /db2logs/
db2 ROLLFORWARD DATABASE <DBNAME> TO END OF LOGS AND STOP

Step 2 — Set HADR Parameters

-- On PRIMARY
UPDATE DB CFG FOR <DBNAME> USING HADR_LOCAL_HOST  '<hadr_ip_primary>'
UPDATE DB CFG FOR <DBNAME> USING HADR_LOCAL_SVC   '51000'
UPDATE DB CFG FOR <DBNAME> USING HADR_REMOTE_HOST '<hadr_ip_standby>'
UPDATE DB CFG FOR <DBNAME> USING HADR_REMOTE_SVC  '51000'
UPDATE DB CFG FOR <DBNAME> USING HADR_REMOTE_INST '<standby_instance>'
UPDATE DB CFG FOR <DBNAME> USING HADR_SYNCMODE    SYNC
UPDATE DB CFG FOR <DBNAME> USING HADR_TIMEOUT     120
UPDATE DB CFG FOR <DBNAME> USING HADR_PEER_WINDOW 120
UPDATE DB CFG FOR <DBNAME> USING LOGARCHMETH1 'DISK:/db2archive/<DBNAME>/'
db2set DB2_HADR_ROS=YES   -- Reads on Standby (optional)
-- On STANDBY (LOCAL/REMOTE swapped)
UPDATE DB CFG FOR <DBNAME> USING HADR_LOCAL_HOST  '<hadr_ip_standby>'
UPDATE DB CFG FOR <DBNAME> USING HADR_LOCAL_SVC   '51000'
UPDATE DB CFG FOR <DBNAME> USING HADR_REMOTE_HOST '<hadr_ip_primary>'
UPDATE DB CFG FOR <DBNAME> USING HADR_REMOTE_SVC  '51000'
UPDATE DB CFG FOR <DBNAME> USING HADR_REMOTE_INST '<primary_instance>'
UPDATE DB CFG FOR <DBNAME> USING HADR_SYNCMODE    SYNC
UPDATE DB CFG FOR <DBNAME> USING HADR_TIMEOUT     120

Step 3 — Start HADR (standby first)

START HADR ON DATABASE <DBNAME> AS STANDBY   -- on standby node
START HADR ON DATABASE <DBNAME> AS PRIMARY   -- on primary node

Step 4 — Verify

SELECT HADR_ROLE, HADR_STATE, HADR_SYNCMODE, STANDBY_LOG_GAP
FROM TABLE(MON_GET_HADR(NULL)) AS T;
-- Expected: HADR_STATE = PEER, STANDBY_LOG_GAP = 0 (SYNC)
HADR_STATE = PEER means both nodes are fully synchronised and HADR is operating normally.

Automatic Client Reroute (ACR)

Redirect application connections automatically after a HADR takeover.

ACR allows the Db2 client driver to reconnect to the new primary after takeover without application changes.

Configure Alternate Server

-- Run on each client node
UPDATE ALTERNATE SERVER FOR DATABASE <DBNAME>
  USING HOSTNAME <standby_hostname> PORT <port>

LIST DATABASE DIRECTORY  -- verify

ACR Behaviour by Client State

Client State at FailoverACR Behaviour
Idle connection (no active transaction)Automatically retried to alternate server — transparent to application
Active transaction in progressTransaction rolled back; connection retried to new primary
No ACR configuredSQL30081N — manual reconnect required
ACR ≠ Zero-Downtime ACR eliminates manual reconnection but active transactions are still rolled back. Design applications to retry on connection failure.

JDBC Connection String

jdbc:db2://<primary_host>:50000/<DBNAME>:
  clientRerouteAlternateServerName=<standby_host>;
  clientRerouteAlternatePortNumber=50000;
  enableClientAffinitiesList=0;

Shell Check Script

#!/bin/bash
STATE=$(db2 -x "SELECT HADR_STATE FROM TABLE(MON_GET_HADR(NULL)) AS T" | tr -d ' ')
if [ "$STATE" != "PEER" ]; then
  echo "CRITICAL: HADR_STATE=$STATE"; exit 2
fi
echo "OK: HADR_STATE=PEER"; exit 0

Failover Procedures

Before any takeover — confirm HADR_STATE and log gap with MON_GET_HADR. Document the reason for takeover.

Graceful Takeover (Planned Maintenance)

Use when primary is reachable and standby is in PEER state. No data loss.

SELECT HADR_STATE, STANDBY_LOG_GAP FROM TABLE(MON_GET_HADR(NULL)) AS T;
TAKEOVER HADR ON DATABASE <DBNAME>
SELECT HADR_ROLE, HADR_STATE FROM TABLE(MON_GET_HADR(NULL)) AS T;

Forced Takeover (Emergency — Primary Unreachable)

DATA LOSS POSSIBLE Data loss equal to the current log gap will occur. Isolate the old primary from the network before executing to prevent split-brain. 
-- Isolate old primary (fence from network first!)
TAKEOVER HADR ON DATABASE <DBNAME> BY FORCE

Re-integrate Old Primary as New Standby

db2stop force                                    -- on old primary
START HADR ON DATABASE <DBNAME> AS STANDBY      -- restart as standby
SELECT HADR_STATE, STANDBY_LOG_GAP FROM TABLE(MON_GET_HADR(NULL)) AS T;
-- Wait for REMOTE_CATCHUP -> PEER

Failover Decision Tree

SituationActionRisk
Planned maintenanceGraceful TAKEOVER HADRNone
Primary unreachable, standby PEERConfirm isolation, then TAKEOVER BY FORCEPossible log gap loss
Primary unreachable, standby DISCONNECTEDRestore standby from backup first, then catch upHigher data loss risk
Both nodes unreachableRestore from latest backup to new nodeData loss up to last backup

1. Overview

IBM DataStage (part of IBM DataStage as a Service / CP4D / standalone) is an ETL/ELT platform whose HA design spans three distinct layers: the conductor/worker parallel engine, the repository and metadata store, and the job scheduler and project services. Failures in any layer require a different resilience approach.

GoalTarget
Job restart on worker failureAutomatic (within current job run)
Service recovery (conductor)< 5 minutes (Tier 2)
Repository RPO0 s (synchronous DB replication)
Metadata / project RPO< 60 s
Scheduled job continuityResume from last checkpoint after recovery

3. HA Topology

The active conductor dispatches work to the worker pool. The standby conductor mirrors configuration and is ready to take over. The repository is backed by a highly available database (Db2 HADR or PostgreSQL streaming replication).

4. Parallel Engine Resilience

Failure ScenarioBehaviourAction Required
Worker node crash during jobConductor detects lost worker; job aborted with error codeJob re-triggered from last checkpoint (if configured)
Worker node removed (planned)In-flight partitions drained; node removed from poolReduce partition count or add replacement worker before removal
Active conductor crashCluster manager promotes standby conductor; in-flight jobs abortedRestart jobs; investigate conductor logs
Shared filesystem unavailableAll jobs fail; conductor cannot load job executablesRestore HA filesystem; no job data lost if NFS/GPFS is HA-backed
Repository DB unavailableJob scheduling and Designer blocked; running jobs unaffected until completionTrigger DB failover; DataStage services reconnect automatically

Checkpointing

For long-running jobs, enable restart capability using sequential file stages with restart markers, or partition-level checkpoints in the job design. This limits re-work to the last checkpoint rather than a full restart.

Design Jobs for Restartability Always design DataStage jobs to tolerate a restart from a known-good point. Use surrogate key lookup stages idempotently, and mark intermediate files as persistent so they survive a conductor failover.

The DataStage repository database stores all job designs, project metadata, run history, and operational parameters. It is the single most critical persistence layer — a repository outage blocks all new job launches and Designer activity.

8. Recovery Procedures

8.1 Conductor Failover

# Verify standby conductor is active (Pacemaker example)
pcs status

# If automatic failover did not trigger:
pcs resource move ds-conductor-vip <standby_node>

# After failover — restart DataStage engine services on new active node
./dsenv && bin/uv -admin -start

8.2 Failed Job Recovery

# List failed jobs in a project (Director CLI)
dsadmin -domain <domain> -user <admin> -password <pwd> \
        -listjobs <project>

# Re-run from last checkpoint (if job supports restart)
dsjob -run -mode RESTART -project <project> -job <jobname>

# Force reset job state before re-run if needed
dsjob -run -mode RESET -project <project> -job <jobname>

8.3 Repository Recovery

Follow the Db2 HADR takeover procedure (see Db2 HADR tab, section 10) for Db2-backed repositories. For CP4D PostgreSQL repositories, trigger Patroni failover via the CP4D operator:

# CP4D / OpenShift — trigger Patroni failover
oc exec -n <namespace> <patroni-leader-pod> -- \
  patronictl failover --master <current-leader> --candidate <new-leader> --force
